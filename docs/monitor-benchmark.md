# 隐藏态监控 benchmark

这个 benchmark 对同一个 `SystemMonitor` 分别执行完整快照与轻量摘要，记录稳态同步采样工作的 median、p95 和 maximum wall time。轻量摘要刷新 CPU、内存、磁盘 I/O、网络吞吐、卷容量和低频传感器缓存，但不枚举、排序或序列化进程，也不扫描网络连接明细。

```bash
cargo run --locked --manifest-path src-tauri/Cargo.toml --release \
  --example monitor-benchmark -- 20 250
```

可选的第二个参数是两次采样之间的等待毫秒数，默认 250 ms，用于跨过 `sysinfo` 的最小 CPU 刷新窗口；等待时间不计入采样 wall time。比如 `20 250` 会让完整和轻量路径分别运行约 5 秒。

输出中的采样时间单位是微秒。测试应固定机器、电源模式、后台负载和 CoreRobin commit，并至少保存三次原始结果。这个微基准不包含 Tauri IPC、前端渲染或 5 秒真实定时器节奏，因此只能用于比较两种后端采样路径的同步工作量，不能替代 Instruments 等整机 CPU/能耗 profile。

按当前产品节奏，前台最低间隔是 500 ms，隐藏态轻量摘要间隔是 5 s；网络连接扫描在隐藏态停止。发布前的整机 profile 应同时验证：

- 隐藏后不再调用完整快照和网络连接明细命令；
- tray/companion 最晚约 5 秒获得一次轻量摘要；
- 恢复显示后立即请求完整快照；
- pause 同时停止完整快照和轻量摘要；
- 相同环境下保留三次 benchmark 原始结果，不用单次数据宣称跨机器阈值。

## 2026-07-15 首轮记录

环境为 macOS 26.3 (25D125)、Mac15,6、18 GiB RAM；源码状态是 `b4e7367` 之后的 WP-8 工作树。命令为 `monitor-benchmark -- 20 250`，每轮约有 553–568 个进程。三次 release 结果如下：

| 轮次 | 完整快照 median / p95 / max | 轻量摘要 median / p95 / max |
| --- | --- | --- |
| 1 | 8,995 / 20,917 / 22,114 µs | 40 / 334 / 46,210 µs |
| 2 | 14,139 / 21,760 / 49,135 µs | 47 / 107 / 41,778 µs |
| 3 | 8,128 / 14,713 / 15,865 µs | 55 / 98 / 108,971 µs |

轻量路径的稳态 median 比完整快照低两个数量级，并且隐藏态调度从最高每秒 2 次降到每 5 秒 1 次；它不再刷新进程和网络列表。轻量路径的单次 max 仍会包含低频传感器刷新等慢路径，因此这组数据不能替代整机 CPU/能耗 profile，也不用于自行确定 D10 的最终跨机器发布阈值。fake timer 测试另行断言隐藏态不调用完整快照或网络连接命令、显示时立即恢复完整快照、pause 优先于两种采样。

这组首轮数据早于 2026-07-16 的统一健康状态服务改造；当时的轻量摘要尚未刷新磁盘 I/O 和网络吞吐。实现改造后必须重新记录数据，不能直接沿用上表宣称新的轻量路径仍有相同比例。

## 2026-07-16 健康摘要改造后记录

同一环境，命令仍为 `monitor-benchmark -- 20 250`。轻量摘要已经包含磁盘 I/O 和网络吞吐，
每轮约有 569–582 个进程：

| 轮次 | 完整快照 median / p95 / max | 健康摘要 median / p95 / max |
| --- | --- | --- |
| 1 | 14,840 / 20,613 / 24,822 µs | 3,353 / 7,120 / 88,591 µs |
| 2 | 18,941 / 26,404 / 37,527 µs | 7,020 / 11,793 / 79,099 µs |
| 3 | 25,130 / 27,738 / 28,286 µs | 2,067 / 4,743 / 51,134 µs |

三轮 median 的中位数为完整快照 18,941 µs、健康摘要 3,353 µs，健康摘要约为完整快照
同步工作时间的 18%。它不再具有旧版的两个数量级差距，但在 5 秒后台节奏下仍避免了进程枚举、
排序和序列化。摘要 max 继续受低频传感器慢路径影响，因此仍需用 Instruments 验证整机能耗，
不能把这组微基准当成发布级功耗结论。

三轮可比原始结果可以通过 `pnpm performance:baseline` 统一写入带 commit 与机器信息的
JSON；发布前整机 profile、冷启动和自动门禁边界见
[发布冒烟与性能门禁](release-smoke-and-performance.md)。
