# 日常模式「值得留意」事件生命周期设计

## 背景

日常模式当前直接把每次系统采样产生的诊断结果转换成首页事项。系统默认每秒采样一次，因此只要最新一个样本回落到阈值以下，首页数量就可能从 3 项立即变为 1 项；用户点击后，详情页又会重新读取实时诊断，导致刚才的问题看起来像是凭空消失。

本设计把“原始信号”和“需要用户留意的事件”分成两层：

- 诊断层继续按高频采样生成候选证据，不直接承诺用户需要处理。
- 事件层负责确认、保持、恢复和留存，首页、顶部状态和引导详情只消费事件层。

## 参考方案

- [Prometheus alerting rules](https://prometheus.io/docs/prometheus/latest/configuration/alerting_rules/) 使用 `for` 把持续满足条件的告警从 pending 提升为 firing，并用 `keep_firing_for` 避免一次正常采样就宣布恢复。
- [Grafana alert lifecycle](https://grafana.com/docs/grafana-cloud/alerting-and-irm/alerting/fundamentals/alert-rule-evaluation/) 明确区分 Normal、Pending、Alerting、Recovering；[recovery threshold](https://grafana.com/docs/grafana/latest/alerting/fundamentals/alert-rules/queries-conditions/) 使用与触发阈值不同的恢复阈值，避免在边界附近反复切换。
- [Netdata alert delay](https://learn.netdata.cloud/docs/alerts-%26-notifications/alert-configuration-reference) 分别设置状态上升和下降延迟，避免告警通知频繁翻转。

CoreRobin 采用三者共同的核心原则：持续确认、恢复回差、恢复确认和稳定事件身份；不采用 Netdata 的倍增延迟，因为本地桌面场景需要让恢复反馈保持可预期。

## 用户可见状态

```text
候选（不展示） -> 已确认（计数并展示） -> 恢复确认中（继续计数） -> 已恢复（退出计数，详情短期保留）
                      ^                         |
                      +---- 条件再次满足 -------+
```

### 候选

- 只在内部保存，不进入首页数量。
- 不改变首页和状态栏结论；用户主动运行“检查一下”时可以明确看到仍在观察，避免把候选信号说成待处理事项。
- 条件中断或采样间隔异常时重新计时，不能把休眠期间的时间误算为连续异常。

### 已确认

- 进入首页总数和顶部状态。
- 使用稳定的事件 ID；同一资源的指标变化只更新证据，不创建新事项。
- 严重度可升级，但不会因为一次回落直接消失。

### 恢复确认中

- 当前值已经越过恢复阈值，但恢复持续时间还没有满足。
- 仍计入未解决事项，文案改为“指标已回落，正在确认是否恢复”。
- 如果条件再次满足，返回“已确认”，不创建新事件，也不重复通知。

### 已恢复

- 从首页数量中移除。
- 在内存中保留 5 分钟，确保已经打开的详情仍能显示原始原因、时间和“已恢复，无需处理”。
- 详情不得继续提供基于旧进程快照的关闭操作。

## 触发策略

| 事项 | 进入策略 | 说明 |
| --- | --- | --- |
| CPU、磁盘 I/O、网络吞吐 | 诊断层持续 10 秒后，再由事件层确认 10 秒 | 总体约 20 秒，过滤短任务和突发传输 |
| 高连接数网络异常 | 持续 10 秒 | 现有诊断对此是即时判断，事件层补足持续确认 |
| 内存压力 | 普通压力持续确认；极低可用内存且大量交换时立即确认 | 避免在真正资源枯竭时延迟提醒 |
| 空间不足 | 立即确认 | 磁盘容量是缓慢变化状态，不需要额外等待 |
| 温度 | attention 持续 10 秒，urgent 持续 3 秒 | 兼顾传感器抖动与高温响应速度 |
| 低电量 | 立即确认 | 电量是缓慢单向变化状态 |
| 阻止休眠 | 操作系统报告持续至少 120 秒后确认 | 播放、索引和短任务不应成为待处理事项 |

无有效持续时间的休眠阻止信息不升级为首页事项，因为无法证明它是持续状态。

## 恢复策略与回差

默认恢复确认时间为 30 秒；低电量在接入电源或电量回升后确认 10 秒。缺少新数据时保持当前事件，不把“没有读到”解释成“已经恢复”。

| 事项 | 触发阈值 | 恢复阈值 |
| --- | --- | --- |
| CPU | 75% | 低于 65% |
| 磁盘 I/O | 50 MiB/s | 低于 35 MiB/s |
| 网络吞吐 | 25 MiB/s | 低于 18 MiB/s |
| 网络连接 | 500 | 低于 400 |
| 温度 | 75°C | 不高于 70°C |
| 电量 | 不高于 20% 且放电 | 接入电源或高于 25% |
| 空间 | 使用率不低于 85% 或可用不高于 10 GiB | 使用率低于 80% 且可用高于 15 GiB |
| 内存 | 现有真实压力条件 | 可用内存恢复到至少 15% |

恢复阈值和恢复持续时间同时满足后才完成恢复。

## 计数和归因

- 首页标题使用完整的未解决事件数量，不能使用“最多展示 3 条”的列表长度。
- 首页可以只突出一个最高优先级事件，但总数必须准确。
- 应用是 CPU、内存或磁盘事件的可能原因，不再作为额外独立事项重复计数。
- 多个阻止休眠的应用合并为一个“阻止休眠”事件，详情展示当前最主要的应用。
- 排序按“正在发生的 urgent、正在发生的 attention、恢复确认中”排列；同等级保持事件首次确认顺序，避免卡片跳动。

## 详情上下文

从首页进入详情时传递具体事件，而不是只传递 `slow`、`heat` 等意图：

- 固定事件 occurrence ID、首次观察时间、确认时间、最近命中时间和峰值严重度。
- 事件仍在发生时展示最新证据。
- 事件进入恢复确认时展示恢复状态，并保留触发时证据。
- 事件已恢复时明确说明“该情况已经恢复，无需处理”，不展示基于旧快照的操作按钮。
- 用户主动从“帮我解决”进入时仍使用实时检查流程，不伪造事件上下文。

## 与既有告警系统的边界

`resourceAlerts.ts` 继续负责 CPU、内存和容量的桌面通知与历史事件；新的日常事件层负责所有日常首页事项。两者采用相同的 pending、hysteresis、recovering 原则，但阈值和展示语义不同：通知强调是否打扰用户，日常事件强调首页承诺是否稳定。

所有日常模式入口必须统一消费事件层，避免首页、顶部状态和引导页各自重新解释实时样本。

## 统一应用健康状态服务

事件生命周期不属于任何窗口。CoreRobin 使用一个长生命周期健康引擎生成事件，Rust
应用状态保存最后一份版本化展示快照，并将它分发给主窗口、状态栏面板和桌面小伙伴。
外观主题与语言仍是独立服务，不能承载健康状态。

```text
完整样本（前台） ─┐
                  ├─> Health Engine ─> DailyIncident[] ─> 主窗口完整视图
健康摘要（后台） ─┘          │
                             └─> HealthStateUpdate
                                      │
                                      v
                              Tauri AppState Registry
                                 │             │
                                 v             v
                              状态栏面板     桌面小伙伴
```

### 状态所有权

- 健康引擎是唯一判定者，统一执行候选确认、恢复回差、恢复确认和事件留存。
- 主窗口消费完整事件对象，但不再负责向其他窗口直接广播临时摘要。
- Rust 注册表为展示快照分配单调递增的 `revision`，保存当前值并广播变更。
- 状态栏面板和桌面小伙伴只投影 `HealthStateSnapshot`，不得重新读取指标下结论。
- 点击辅助界面时使用 `primaryIncident.occurrenceId` 作为精确跳转上下文；没有主事件时才回到概览。

### 展示快照契约

`HealthStateSnapshot` 至少包含：

- schema 版本、服务 revision、采样时间和前台/后台采样模式；
- `observing / normal / attention / urgent` 整体等级和主要原因；
- 已确认数量、候选数量、恢复确认中数量；
- 主事件的 occurrence ID、阶段、严重度、意图和关键时间；
- CPU、内存、存储、温度和电池的紧凑指标；
- 暂停状态。

展示快照不包含文件内容、进程命令行或完整诊断证据。主窗口仍从内存中的完整事件读取这些信息。

### 初始化与顺序保证

Tauri 事件不是保留消息，辅助窗口不能假设自己一定赶上首次广播。每个辅助窗口启动时必须：

1. 先注册 `core-robin:health-state-changed` 监听器；
2. 再调用 `get_health_state` 读取注册表当前值；
3. 同时到达时只接受 revision 更高的状态；
4. 卸载时取消监听。

主窗口发布使用单通道串行队列。采样快于 IPC 时只保留最新的待发布状态，避免旧请求后完成并覆盖新状态。

### 隐藏态采样

隐藏主窗口后继续以 5 秒间隔读取健康摘要。摘要刷新 CPU、内存、磁盘 I/O、网络吞吐、
卷容量和传感器，但不枚举进程，也不扫描网络连接明细：

- 可以继续确认或恢复 CPU、内存、空间、磁盘吞吐、网络吞吐、温度、电量事件；
- 已存在的连接数事件在没有新连接明细时保持，不把未知状态误判为恢复；
- 新事件在后台可能暂时没有应用归因，主窗口恢复显示后的完整样本再补充归因；
- 主事件 occurrence ID 在前后台切换时保持稳定。

该策略延续隐藏态低能耗目标，同时消除“指标更新了、事件生命周期却被冻结”的不一致。

### 故障与降级

- 尚无快照时，辅助界面显示连接中，不使用硬编码的正常状态。
- Rust 注册表暂时不可用时，主窗口继续显示本地完整事件；发布器保留最新状态并等待下一次采样重试。
- 采样暂停时保留最后结论并明确携带 `paused`，不伪造新采样时间。
- schema 不兼容或数量关系非法的更新由 Rust 拒绝，不能污染所有展示端。

## 验收标准

1. CPU 连续异常并出现首页事项后，单个正常样本不会减少数量。
2. 指标在触发阈值和恢复阈值之间波动时，事件保持“已确认”。
3. 指标低于恢复阈值后进入“恢复确认中”，持续 30 秒才退出首页数量。
4. 恢复期间再次异常会回到“已确认”，不创建第二个事项。
5. 用户点击后，即使事件恢复，详情仍显示原始事件和明确恢复结论。
6. 首页显示的是完整事件总数，不受重点列表展示上限影响。
7. 诊断原因中的应用不会再被重复算成另一个事项。
8. 小于 120 秒的休眠阻止不会出现在首页。
9. 缺失传感器或连接数据不会自动关闭正在发生的事件。
10. 主窗口隐藏后，轻量样本仍能完成事件确认和恢复确认。
11. 状态栏面板和桌面小伙伴显示同一个 revision、数量、阶段和主要原因。
12. 辅助窗口晚于首次广播启动时，可以通过当前快照立即恢复状态。
13. 快速连续发布不会让较旧的健康状态覆盖较新的状态。
